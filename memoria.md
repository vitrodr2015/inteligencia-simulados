## Regras (resumo; a fonte é o `CLAUDE.md`)

- Um passo por vez; plano antes de codar.
- Prova antes de "pronto" (teste passando ou resposta real).
- Nada de segredo no repositório, em log ou em chat.
- Trabalho por branch e PR; nunca commitar na `main`.
- Ação irreversível (merge na `main`, deploy, infraestrutura) só com confirmação explícita, que não vale para a próxima.
- Commit/push só quando o usuário pedir (regra atual do `CLAUDE.md`).
- Sem dependência nova nem antecipar escopo sem avisar e justificar.

## Decisões

- Repositório **público** (necessário para as regras de proteção valerem na conta gratuita).
- Aprovação: o responsável único é o dono do projeto (projeto individual, 0 aprovações exigidas no PR).
- Arquitetura: monólito modular; pacote base `br.simulado.etec`; camadas por domínio: `controller`, `service`, `repository`, `model`, `dto`, `mapper`; `shared`: `config`, `exception`, `security`.
- CI: GitHub Actions (`.github/workflows/ci.yml`) roda `./mvnw -B -ntp verify` em PR e em push na `main`, Java 25.
- Dependabot semanal para Maven (`/etec`) e GitHub Actions.
- Proteção da `main` (ruleset `proteger-main`, ativo): PR obrigatório, check **Build e testes** obrigatório com a branch atualizada, sem force push, sem deleção. Confirmado por push direto recusado.
- Merge de PR: squash.
- CD: adiado; destino de deploy em aberto. Parte de nuvem (AWS) adiada.
- Um único `.gitignore`, na raiz, com padrões de segredo (`.env*`, `application-local.*`, `*.pem`, `*.key`...).
- Configuração: `application.yml` com segredos `${VAR}` sem padrão (`DB_PASSWORD`, `JWT_SECRET`). `ValidacaoDeAmbiente` (listener no `main`) recusa subir sem eles, com `JWT_SECRET` abaixo de 32 caracteres ou com espaço/quebra de linha nas pontas; a mensagem nunca mostra o valor. Teste de higiene lê o `application.yml` real e reprova segredo com valor padrão.
- Configuração local: copiar `etec/config/application-local.yml.example` para `etec/config/application-local.yml` (ignorado) e rodar com `SPRING_PROFILES_ACTIVE=local`.
- Banco: collation `utf8mb4_unicode_ci` (charset `utf8mb4`), declarada na própria migration de cada tabela. Motivo: o contrato 4.1 exige nome de matéria único ignorando maiúsculas e acentos, e o D29 define o filtro `nome` como "contém" também sem distinguir maiúsculas e acentos; uma collation `_ci` faz as duas coisas no próprio banco (índice único e `LIKE`). Consequência: o e-mail também é único sem distinguir maiúsculas. O H2 dos testes rápidos não se comporta igual; isso só é provado contra MySQL real (Módulo 7).
- Banco: nenhum seed em migration (dados de exemplo só no `data.sql` dos testes); tabelas no singular, em português, snake_case, sem acento; colunas de data `criado_em`/`atualizado_em`/`excluido_em` (o `CLAUDE.md` foi alinhado a isso).
- Banco: `public_id` como `BINARY(16)` (o Hibernate valida sem anotações extras e o índice único fica menor; para ver como UUID no SQL, `BIN_TO_UUID()`). Starter de teste de JPA no Boot 4: `spring-boot-starter-data-jpa-test`.
- Erros (Tarefa 04): formato único `ErrorResponse` (`dataHora`, `status`, `erro`, `codigo`, `mensagem`; `campos` e `detalhes` somem do JSON quando nulos), produzido só pelo `GlobalExceptionHandler` (estende `ResponseEntityExceptionHandler`, tudo em português e sempre em JSON, mesmo com `Accept: application/xml`). `ApiException` é a base das exceções de negócio (`ResourceNotFoundException` 404, `InvalidRequestException` 400, `ConflictException` 409). Os códigos de negócio (`MATERIA_NOME_DUPLICADO` etc.) entram no `CodigoErro` junto com cada recurso. O 500 é sempre genérico e a pilha vai só para o log. 401 e 403 nascem nos filtros de segurança e ficam para o Módulo 10.
- Clock: bean `Clock` em UTC em `shared.config` (`ClockConfig`), usado para o `dataHora` do erro e para a auditoria; os testes fixam o Clock.
- Auditoria do `Usuario`: `@CreatedDate`/`@LastModifiedDate` do Spring Data (`AuditoriaConfig`, com `@EnableJpaAuditing` e um `DateTimeProvider` sobre o `Clock`), no lugar de `@PrePersist`/`@PreUpdate`; o `public_id` é gerado no construtor. O `DateTimeProvider` trunca o instante para milissegundos (ver o achado do `DATETIME(3)` abaixo). **Todo `@DataJpaTest` que persista entidade com auditoria precisa de `@Import(AuditoriaConfig.class)` e de um Clock fixo** (`@TestConfiguration`), porque os testes de fatia (`@DataJpaTest`, `@WebMvcTest`) não carregam classes `@Configuration`.

Sem isso, um POST em rota inexistente viraria 405, porque o tratador de arquivos estáticos só aceita GET e HEAD. O Swagger foi conferido na Tarefa 05 (springdoc 3.2.0): a interface responde 200 em `/swagger-ui/index.html` (e `/swagger-ui.html` redireciona), porque o springdoc registra os próprios mapeamentos; o `add-mappings: false` não atrapalha.

- Matéria (Tarefa 05) e padrão de entidade: `V2__create_table_materia.sql` (`id` BIGINT interno, `public_id BINARY(16)` único, `nome` com índice único e collation `utf8mb4_unicode_ci`, `descricao`, `ativo` BOOLEAN default TRUE, `criado_em`/`atualizado_em` DATETIME(3)); o Hibernate validou `binary(16)` e `tinyint(1)` com `ddl-auto: validate`. Padrão das entidades (`Usuario`, `Materia`): `public_id` gerado no construtor, `@EntityListeners(AuditingEntityListener.class)` com `@CreatedDate`/`@LastModifiedDate` (Clock truncado em milissegundos), `@Column` com nome explícito, sem setters (métodos de negócio). Service com `@Transactional(readOnly = true)` na classe e `@Transactional` nas escritas; mapper escrito à mão; o `DELETE` é atômico, numa instrução só (`@Modifying` por `public_id`, 0 linhas = 404), nunca ler e depois apagar; nome duplicado = checagem prévia e também a violação do índice único (corrida), ambos 409 `MATERIA_NOME_DUPLICADO`.
- Achado do `DATETIME(3)` no MySQL real: o `Instant.now()` tem precisão menor que 1 ms; a API trunca ao serializar, mas o MySQL ARREDONDA ao gravar em `DATETIME(3)`, então o POST devolvia `.850` e o GET seguinte `.851`. Corrigido truncando para milissegundos na `AuditoriaConfig` (com `AuditoriaConfigTest`). O H2 dos testes não pega isso porque o esquema dele é gerado pelo Hibernate (`create-drop`, timestamp com precisão maior), não pelo `DATETIME(3)` da migration; só o MySQL real arredonda. Regra: toda data gravada em `DATETIME(3)` nasce truncada em milissegundos.
- `JacksonConfig` (formato global de datas, sem anotar campo a campo): `Instant` sai SEMPRE em UTC com exatamente 3 casas de milissegundos, truncando, inclusive quando são zero (serializador próprio, só na saída; a leitura de `Instant` segue o padrão do Jackson); `LocalDate` é lida de forma estrita em `uuuu-MM-dd` (`withConfigOverride` com `lenient=false`): `2000-02-30`, `2001-02-29` e `2000-2-3` dão 400 (`CORPO_ILEGIVEL`), nunca corrigidas em silêncio. O padrão de datas do Java (resolução SMART) corrige `02-30` para `02-29`, por isso o `lenient=false`. Mecanismo: `JsonMapperBuilderCustomizer` (`org.springframework.boot.jackson.autoconfigure`) com `SimpleModule`; testado com o `JsonMapper` real, por MockMvc e por `curl` no banco real.
- Rotas: o caminho `/api/v1/...` fica explícito em cada controller (`@RequestMapping("/api/v1/materias")`). Um prefixo global por pacote quebraria os controllers falsos dos testes (que já têm `/api/v1`) e deixaria dúvida sobre o que fica fora (actuator, Swagger, `/error`).

- Achados da Tarefa 06: (1) a violação de `CHECK` do MySQL (erro 3819) chega como `UncategorizedSQLException`, e não como `DataIntegrityViolationException` (que é a da violação de índice único); o teste do `CHECK` olha a causa raiz. (2) Concorrência no MySQL real: 20 `DELETE` simultâneos dão 1 × 204 e 19 × 404, e 20 `POST` com o mesmo nome dão 1 × 201 e 19 × 409 (`MATERIA_NOME_DUPLICADO`); 15 repetições seguidas sem nenhum 500, então o `try/catch` em volta do `saveAndFlush` já basta e o service não precisou de correção (os testes ficam com `@RepeatedTest(3)`). Limite conhecido: com `POST` simultâneos de mesmo nome, o InnoDB pode abortar uma das transações por deadlock de índice único (erro 1213); não apareceu em 30 execuções, mas depende de tempo e pode aparecer em outra máquina. O Spring o traduz como `CannotAcquireLockException` (um `PessimisticLockingFailureException`), que hoje NÃO é tratada e cairia no 500 genérico. Tratamento previsto, só se aparecer (não implementado): no `MateriaService.criar`, capturar também `CannotAcquireLockException` e, numa nova transação, refazer a checagem do nome: se já existe, 409 `MATERIA_NOME_DUPLICADO`; se não, repetir a criação uma única vez.

Os testes web usam `@SpringBootTest` com `@AutoConfigureMockMvc` (`org.springframework.boot.webmvc.test.autoconfigure`) e não usam `@Transactional` (limpam com `deleteAll`), para o teste de concorrência (`@RepeatedTest(5)`, 12 DELETE simultâneos) enxergar dados confirmados. O springdoc fica desligado no `application.yml` de teste; os testes do Swagger ligam por propriedade.
- Paginação reutilizável (Tarefa 07), em `br.simulado.etec.shared.paginacao`: `PaginaResponse<T>` (envelope, campos na ordem `conteudo`, `pagina`, `tamanho`, `totalElementos`, `totalPaginas`; `PaginaResponse.de(page, conversor)`), `CamposOrdenaveis` (lista FIXA de campos ordenáveis do recurso mais a ordenação padrão), `ConversorDePaginacao.converter(page, size, sort, campos)` (devolve um `Pageable` seguro) e `Filtros` (`contem`, `igual`, `booleano`, `semFiltro`). **Como um recurso novo usa:** (1) o repositório estende `JpaSpecificationExecutor<Entidade>`; (2) o service declara `public static final CamposOrdenaveis CAMPOS_ORDENAVEIS = CamposOrdenaveis.de(Sort padrão, "campo1", "campo2")` e um `listar(filtros, Pageable)` que combina `Specification.allOf(Filtros.contem(...), Filtros.igual(...))` e chama `repositorio.findAll(spec, pageable)`; (3) o controller recebe `page`, `size`, `sort` e os filtros como `String` (`@RequestParam(required = false)`), chama `ConversorDePaginacao.converter` e `Filtros.booleano` e devolve `PaginaResponse.de(pagina, Mapper::paraResponse)`; (4) a interface `*ControllerDocs` documenta 200 e 400 e os parâmetros com descrição e SEM `example`; (5) o teste de integração cria dados com um token único no nome e filtra por esse token (o banco é compartilhado). Exemplo completo: a listagem da Matéria.
- Regras do conversor de paginação: tamanho padrão 20 e máximo 50 SÓ nas constantes de `ConversorDePaginacao` (o `spring.data.web.pageable` do yml era uma segunda fonte e foi removido); `size` acima de 50 é reduzido a 50 sem erro; `page` ou `size` negativo, `size=0` e valor não numérico = 400 `PARAMETRO_INVALIDO`; `sort` = `campo,direção` (sem direção vale asc; a direção vale em qualquer caixa), só com campos da lista do recurso, e qualquer outro valor = 400 `ORDENACAO_INVALIDA` (a mensagem lista os campos aceitos e não repete o valor); o desempate por `id` (o id numérico interno) é SEMPRE acrescentado, em ordem crescente. `PropertyReferenceException` (`org.springframework.data.core`, pacote novo do Spring Data 4) vira 400 `ORDENACAO_INVALIDA` por defesa. O filtro `nome` em branco equivale a filtro ausente; `ativo` só aceita `true` ou `false` (outros valores, como 1 ou yes, = 400).
- Achados da Tarefa 07: (1) o resolvedor padrão de `Pageable` do Spring CORRIGE EM SILÊNCIO os valores inválidos (`page=-1` vira 0, `size=0` vira o padrão, `size` não numérico é ignorado), e o contrato manda 400; por isso o conversor é próprio e os parâmetros chegam como texto. (2) `page` gigante dava 500: o Spring Data JPA falha com `Page offset exceeds Integer.MAX_VALUE` quando página x tamanho passa de 2^31-1. O conversor limita a página à maior cujo deslocamento cabe num inteiro (200 vazio), e o `pagina` do envelope devolve a página limitada, e não a pedida. (3) Sem o desempate por id, percorrer 30 itens com o mesmo `criado_em` devolveu só 14 distintos (16 repetições entre páginas) no MySQL real: a paginação fica instável.
- `Specification` em vez de consultas derivadas (Tarefa 07): os filtros são opcionais e combináveis. Com métodos derivados seria um método por combinação (nome, ativo, nome+ativo...), que dobra a cada filtro novo; com `Specification` cada filtro é uma peça e o recurso só as compõe com `allOf`. O escape do LIKE é explícito e único, em `Filtros.contem` (`EscapeCharacter.DEFAULT`: `%`, `_` e `\` valem como texto), e não há SQL concatenado. O "contém" respeita a collation da coluna: no MySQL com `utf8mb4_unicode_ci` ignora maiúsculas e acentos (o H2 não ignoraria, por isso a listagem é provada só no MySQL real). A ordem alfabética também segue a collation.
- Formato da resposta (Tarefa 08), JSON previsível para quem consome:
  - **Só JSON.** Nenhuma dependência de XML, YAML ou HATEOAS foi adicionada. Mas o classpath JÁ trazia dois conversores sem ninguém pedir: o de XML (`Jaxb2RootElementHttpMessageConverter`, por causa do `jaxb-runtime` do Hibernate) e o de YAML (`MappingJackson2YamlHttpMessageConverter`, por causa do `jackson-dataformat-yaml` 2.21.8 que o springdoc traz). Sem tratamento, um endpoint sem `produces` responderia YAML ou XML. `shared/config/SomenteJsonConfig` os remove (`configureMessageConverters(HttpMessageConverters.ServerBuilder)`, API do Spring 7), e então `Accept: application/xml` ou `application/yaml` dá 406 no formato padrão. `ConversoresDeMensagemTest` falha se um conversor de XML, YAML, HAL, Smile, CBOR ou Atom voltar a ser registrado.
  - **Achado dos dois conversores extras e o guarda.** Os conversores de YAML (via springdoc) e de XML (via Hibernate/JAXB) já estavam no classpath sem ninguém pedir; o `SomenteJsonConfig` existe para removê-los, e por isso o 406 vale mesmo num endpoint sem `produces`. **Toda dependência nova pode trazer conversores** (qualquer biblioteca com Jackson dataformat, JAXB, Smile, CBOR, Atom...): o `ConversoresDeMensagemTest` é o guarda e precisa continuar passando; se ele falhar depois de uma dependência nova, ajustar o `SomenteJsonConfig`, não o teste. A rota `/v3/api-docs.yaml` do springdoc continua respondendo 200 (coberta em `SwaggerLigadoTest`), porque ela devolve texto, sem passar pelo conversor de YAML.
  - **404, 405 e 415 em JSON (provado).** Rota inexistente, método não permitido e tipo de corpo não suportado respondem no formato padrão de erro, em JSON, mesmo com `Accept: application/xml` ou `application/yaml` (web e integração). **Pendência para os Módulos 10 e 11:** provar que o **401 e o 403** também saem em JSON, no formato padrão, com `Accept` de XML ou YAML (o Spring Security responde por fora do `GlobalExceptionHandler`, então `AuthenticationEntryPoint` e `AccessDeniedHandler` precisam escrever o `ErrorResponse` em JSON, e isso exige teste próprio).
  - **Nulos.** Nos DTOs de resposta (`MateriaResponse`, `PaginaResponse`) um campo nulo SAI SEMPRE como `null` (`@JsonInclude(ALWAYS)`, por exemplo `"descricao":null`), para o formato ser estável. No `ErrorResponse` só `campos` e `detalhes` são omitidos quando nulos (`@JsonInclude(NON_NULL)` no próprio componente); os demais campos sempre saem.
  - **Datas são globais, não por campo.** O formato (UTC, 3 casas) vive no `JacksonConfig`; NÃO usar `@JsonFormat` em campo de DTO. O `Instant` sai sempre com 3 casas (`.000` incluído); nanossegundos são truncados.
  - **Ordem dos campos fixa** com `@JsonPropertyOrder` (`com.fasterxml.jackson.annotation`, mesmo no Jackson 3): `MateriaResponse` = id, nome, descricao, ativo, criadoEm, atualizadoEm; `ErrorResponse` = dataHora, status, erro, codigo, mensagem, campos, detalhes; envelope = conteudo, pagina, tamanho, totalElementos, totalPaginas; `CampoInvalido` = campo, mensagem.
  - **Content-Type** é exatamente `application/json` (o Spring NÃO acrescenta `charset`; JSON é UTF-8 por definição) e o JSON sai compacto, sem espaços nem quebras de linha. Nos testes, ler o corpo como UTF-8 explícito.
  - **Como adicionar um recurso novo mantendo o formato:** (1) o DTO de saída é um record com `@JsonPropertyOrder` listando TODOS os campos e `@JsonInclude(JsonInclude.Include.ALWAYS)`; (2) um campo novo entra no FIM da lista de ordem e do record (alterar a ordem de um campo existente quebra quem consome); (3) sem `@JsonFormat` em data; (4) o controller devolve o DTO, nunca a entidade; (5) escrever o teste de TEXTO EXATO (a string inteira, não campo a campo): na camada web, `MateriaFormatoWebTest` (service mockado, `Clock` fixo, id conhecido, texto literal) e, com o MySQL real, `MateriaFormatoIntegracaoTest` (só id e data trocados pelos marcadores `<ID>` e `<DATA>`); copiar um desses modelos para o recurso novo, cobrindo o item com valor, o item com nulo, o envelope da lista e os erros.
  - Sabotagens da tarefa: trocar a ordem de `nome` e `descricao` derrubou 6 testes (3 web e 3 de integração); trocar `ALWAYS` por `NON_NULL` derrubou 4 (os que têm `descricao` nula); a campanha de conversores falhou 2 testes antes do `SomenteJsonConfig` existir.
